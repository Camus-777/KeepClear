# v0.3.2 音频与 DPI 修复

## 启动音频链路测试

本版本追加简化启动音频测试：四段路径实际有进展就通过，不再考核耗时、欠载、队列和回读速率，也没有二次性能复查。仅静音测试期间使用有限容量、保留较新样本的缓冲策略。实际设备/模型异常及超时仍报错。该连通性判定独立于下面的正式运行趋势策略。其余自检模块、麦克风选择和动画沿用当前实现。详见 [STARTUP-INSTALL.md](STARTUP-INSTALL.md)。

## 运行时总排队趋势

观察总软件排队时间，包含输入 FIFO、正在处理的输入块、输出 FIFO、正在重采样/提交的样本及重采样播放队列。队列转移在同一同步边界更新，避免只把输入移到输出就误认为已恢复。此估计不包含模型固有算法延迟、驱动内部等待、网络和对方设备，不能当作端到端延迟。

约每 100 ms 观察一次，比较 1 秒窗口均值。连续至少两个窗口增长、每个增长窗口至少增加 2 ms、累计增加至少 20 ms，且当前总排队达到 200 ms 时进入恢复。稳定的 70–80 ms、短时 70→120→70 ms 及稳定的较高等待均继续播放。观察中断超过 0.5 秒时重置趋势样本，不推测缺失期间的趋势。窗口开始下降或增长不足 2 ms 且低于紧急水位时，结束恢复。

恢复优先删除幅度不超过 0.00001（约 −100 dBFS）且连续至少 20 ms 的处理后安静片段，并保留约 120 ms 队列余量。这是保守的幅度判定，不是说话人识别。正常语音样本按顺序保留。接近 500 ms 总排队时立即处理容量压力，先删安静片段，仍超水位才保留较新处理后音频并约 10 ms 交叉淡出淡入，必要时同步监听。极端情况下可能漏听部分语音。

删除旧的“恢复超过 1 秒即失败”和“30 秒内再积压即失败”规则。输入队列仍有 512 ms 硬上限，处理后 FIFO 容量改为 512 ms，渲染 FIFO 仍为设备采样率的半秒，正常预缓冲仍为 48 ms。容量是可用空间，不代表会主动攒到该值。输出达到容量时清理旧处理后样本；输入确实无法跟上且容量耗尽时明确停止，不直接丢弃模型输入。设备断开、模型异常和现有无响应超时保护继续生效。

处理线程和 Python 模型进程使用 AboveNormal；设备线程继续 MMCSS Audio。模型权重、float32 模型参数和启动连通性测试保持不变；本轮 CPU 执行与控件 DPI 修复见下文。

## 诊断

日志位于 %LOCALAPPDATA%/KeepClear/logs。每秒记录处理耗时均值/P95/P99/最大值、输入/输出积压及高水位、采集回调最大间隔、欠载、间断、恢复次数、跳过的处理后样本和 GC 计数。Python 通过 stderr 输出各模型阶段的调用次数、平均及最大耗时，二进制 stdout 协议保持不变。会话记录版本、构建标识、CPU/系统信息，界面记录 DPI 和实际客户端尺寸。日志不包含麦克风录音；设备/路径等诊断信息对外分享前可自行遮盖。

这些指标用于定位处理、调度、通信和设备停顿，不能仅凭整机 CPU 占用或一次耗时峰值认定根因。缺少驱动状态目录视为无需清理，不再产生预期内的目录不存在错误。

## DPI

启动页以 480×280、主界面以 480×456 的 96-DPI 逻辑尺寸设计。编译产物明确声明 .NET Framework 4.8，配置 PerMonitorV2；窗口、原生控件及自绘品牌/光标/电平使用一致的缩放基准。窗口尺寸按当前 DPI 锁定，DPI 变化后重新布局。

60 组本机模拟覆盖 100%、125%、150%、175%、200% 及回到 100%，含双语和五类界面状态。不修改系统缩放设置，不等同于真实远程桌面/跨屏消息验证。

模型权重、float32 模型参数、双模型顺序、增益/限幅、重采样算法以及驱动包没有改变。当前结果及尚未完成的跨机测试见 [VALIDATION.md](VALIDATION.md)。

## DNS48 CPU 与原生控件补充修复

用户实机日志显示 Ryzen 7 H 260 上 Denoiser 约 20–23 ms/块，整条链约 23–24 ms，超过 16 ms 输入时长，造成持续输入积压。修复选用 ATen CPU 路径，关闭模型 worker 的 oneDNN/MKLDNN 分派。逻辑处理器数至少为 4 时用 2 个计算线程，否则用 1 个，interop 为 1。请求 flush-denormal 并记录返回值。均保持 float32、原始权重和 DNS48 dry=0/num_frames=1，不增加每次启动的性能选路测试。

在本机 Ryzen 7 9700X 上比较 6 种 CPU 配置与纯音、全零、极小幅度和衰减 4 类输入。候选配置的 DNS48 平均约 3.6–3.9 ms/块。完整 C#→Python→双模型的同一份 60 秒混合合成语音测试，平均从 8.610 降至 4.473 ms，P99 从 10.166 降至 6.241 ms，最大从 14.894 降至 7.167 ms。两次输出均 959232 个样本，最大绝对差约 8.94e-8。该比较在本机完成，不能据此声称远端 Ryzen H 260 已解决，需要原机复测。

设备框使用 OwnerDrawFixed，补齐按 DPI 和字体重算 ItemHeight 的逻辑，覆盖句柄创建、字体变化及 DpiChangedAfterParent，主界面布局时再对齐刷新键。托盘菜单在 Opening/Opened 时重申 9 pt 基准和当前 DPI 的内边距，取消无用图标/勾选边栏，避免默认菜单字体或累计缩放造成异常放大。诊断新增 device-ui-dpi、tray-dpi、model-cpu 记录。

60 组布局回归补查选择框文字高度、实际控件高度及刷新对齐。托盘另检查人为放大字体后的重复复位、实际弹出尺寸与截图。实际弹出的菜单使用本机 DPI，报告中单独记录 native_tray_dpi，不把模拟的窗体 DPI 当作实测菜单 DPI。远程桌面和原机 200% 显示仍待复测。

参考 PyTorch 的 [set_flush_denormal](https://docs.pytorch.org/docs/stable/generated/torch.set_flush_denormal.html)、Microsoft 的 [ComboBox.ItemHeight](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.combobox.itemheight?view=netframework-4.8) 和 [ContextMenuStrip](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.contextmenustrip?view=netframework-4.8.1)。

## 托盘文字位置补充修复

针对实际 200% 缩放时退出文字贴左上角的反馈，托盘菜单使用专用系统渲染器，从当前菜单项尺寸和内边距重新计算文字区域，并强制水平/垂直居中，避免沿用 DPI 布局后失效的文字区域。保留原生背景、悬停和禁用绘制。新增 24 组中英文、启用/禁用、多 DPI 的文字像素边界检查，主动传入错误的左上角文字区域验证定位和裁切；真实 200% 机器仍待复测。

## 修复版2的缓冲与诊断优化

采集解码、主输出与监听重采样使用线程独占的可复用缓冲区，所有环形缓冲写入显式传入有效长度。主输出、监听和采集的等待句柄数组也复用。模型公开 Process 接口仍返回独立拥有的数组。重采样 FIR、相位和时钟补偿算法保持一致。

普通日志经后台线程批量写入，队列最多512条，每批32条、每条最多16384字符。队满时丢弃普通记录；故障记录优先并可替换普通记录，全部为故障且仍满时淘汰最旧故障。log-health/log-drop 报告丢弃和写入失败计数。正常退出最多等待2秒刷新日志。磁盘持续阻塞、写入失败或强制结束进程时，日志可能不完整。

worker-health 记录发送、等待首个响应长度、接收/复制三段耗时分布。等待包含模型运算和线程调度，不能直接当成纯通信耗时。每5秒更新模型进程 CPU、工作集、私有内存和线程数；cpu_cores 是 CPU 时间/实际时间，可超过1。KC_METRIC/model-timing 每秒追加进程 CPU 时间与 DNS48 待处理样本数、底层存储字节数、LSTM/卷积状态元素数。只记录计数和尺寸，不记录音频或状态数值。Alkove 原生内部状态未公开，未推测其内存布局。

本轮保留启动连通性判定、CPU执行配置和总排队趋势恢复阈值。稳定70–80毫秒或短暂升到120毫秒后回落继续工作。
